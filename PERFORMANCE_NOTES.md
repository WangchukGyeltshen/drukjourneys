# Performance Notes: DrukJourneys

Evidence for NFR-1 (search and package results within 3 seconds at the 95th percentile), NFR-2 (at least 1,000 concurrent users at peak) and NFR-9 (usable on low-bandwidth connections). Entries are dated and say what was measured, how, and what the result does **not** prove.

---

## 2026-10-06: Load test of the public and staff list endpoints

**What changed before measuring:**

- 15 database indexes added (migration `20261006112124_add_performance_indexes`), matched to the queries the code runs (package browse and filters, "my bookings", document review queue, notification log, and foreign keys that PostgreSQL does not index automatically).
- Every growing list endpoint is paginated (`?page=` and `?pageSize=`, default 20, maximum 100) so no request can pull a whole table.
- gzip/deflate compression for JSON responses over 1 KB.

**Method:** `autocannon@8.0.0` (dev dependency), 15 seconds per run, keep-alive connections with no think time between requests. Test data: 2,004 packages (4 real plus 2,000 generated by `server/prisma/loadtest-data.ts`, removed afterwards with its `clean` command). Server in development mode (`tsx watch`, Node v24.7.0), PostgreSQL local, Windows laptop. The load generator, server and database shared that one machine.

**Results:**

| Endpoint | Connections | Median | 97.5% | 99% | Requests/sec | Errors |
|---|---|---|---|---|---|---|
| `GET /packages` | 10 | 4 ms | 7 ms | 8 ms | ~2,050 | 0 |
| `GET /packages` | 100 | 50 ms | 60 ms | 64 ms | ~1,970 | 0 |
| `GET /packages` | 500 | 272 ms | 296 ms | 308 ms | ~1,840 | 0 |
| `GET /packages` | 1,000 | 556 ms | 963 ms | 967 ms | ~1,455 | 0 |
| `GET /packages?dzongkhag=Paro&category=CULTURAL` | 100 | 48 ms | 55 ms | 58 ms | ~2,040 | 0 |
| `GET /bookings?pageSize=20` (agent token, joins 3 tables) | 100 | 80 ms | 95 ms | 103 ms | ~1,220 | 0 |

Compression, measured separately on `GET /packages`: 1,725 bytes plain versus 726 bytes with `Accept-Encoding: gzip` (about 58% smaller).

**Reading against the NFRs:**

- **NFR-1:** met for the tested endpoints with a wide margin. The 97.5th percentile (stricter than the 95th) stayed under 1 second even at 1,000 connections, against a 3,000 ms requirement.
- **NFR-2:** 1,000 simultaneous connections were served with no errors or timeouts. This is a harsher pattern than 1,000 real users, who pause between requests.
- **NFR-9:** compression and paging cut the data sent per request; this has not yet been measured on a throttled connection.
- Throughput plateaus near 2,000 requests per second while latency grows with connections, which indicates a single Node process is the limit, as expected. Production should run several instances behind a load balancer.

**What this does not prove:**

- Load generator, server and database competed for one machine's CPU, in development mode. These are not production numbers.
- With about 2,000 rows PostgreSQL scans quickly with or without an index, so the test shows no regression but cannot show the indexes' benefit. They matter as the catalog and bookings tables grow.
- Only read endpoints were tested. Not tested: login and register (rate limited by design, and password hashing is CPU-heavy), booking creation, payments and webhooks, document upload and download (encryption cost), email sending, and mixed workloads.
- The database connection pool uses the driver default (about 10 connections). It did not become a bottleneck here, but it should be revisited if write-heavy endpoints are tested.

**Follow-up:**

- Re-run against a deployed environment (separate machines, production mode) before relying on these numbers for NFR-2.
- Rate-limit counters are per process, so a multi-instance deployment needs a shared store (see `SECURITY_NOTES.md`, 2026-10-05).
- Load-test the write paths and document upload once the frontend flow is defined.
